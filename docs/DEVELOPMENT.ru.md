# Руководство по разработке

## Структура репозитория
- `fbx/`: публичный API, транзакции, импорт, pack, journal/recovery.
- `internal/format/`: бинарный формат, кодеки, CRC/hash-помощники.
- `internal/pathutil/`: нормализация и валидация путей.
- `cmd/fbx/`: реализация CLI.
- `tests/`: интеграционные/совместимость/бенчмарки.
- `tests/testdata/vectors/`: канонические векторы совместимости.

## Сборка и тесты
```bash
go build ./...
go test ./...
go test -run TestCanonicalVectors ./tests
go test -run TestPerfGuard ./tests
go test -bench . ./tests
```

Обновление целевых baseline-метрик:
```bash
go test -bench 'BenchmarkEncodeChunkZstd1MiB|BenchmarkContainerAddExtract1MiB|BenchmarkPackMedium(FastUnsafe)?$' -benchmem ./tests
```

Пересоздание векторов:
```bash
go run tests/scripts/gen_vectors.go
```

## Соглашения по коду
- Для изменённых файлов запускать `gofmt -w`.
- Публичный API держать в `fbx/`, внутреннюю реализацию — в `internal/`.
- Для больших входных данных предпочитать потоковый I/O (`io.Reader`/`io.Writer`) вместо полной буферизации.
- Использовать типизированные ошибки; оборачивать их только если сохраняется поведение `errors.Is`.

## Ожидания по тестированию
- На каждое исправление добавлять регрессионный тест.
- При изменениях формата/совместимости обновлять векторы и манифесты.
- Если функциональность зависит от кодека (`zstd`/`lz4`), тесты должны пропускаться при его недоступности.

## Чеклист коммита и PR
- Небольшие фокусные коммиты (`feat:`, `fix:`, `test:`, `docs:`).
- Для изменений поведения указывать ссылки на соответствующие разделы RFC.
- Прикладывать команды валидации (минимум `go test ./...`).
- Для CLI-изменений добавлять конкретный пример команды и ожидаемый фрагмент вывода.
